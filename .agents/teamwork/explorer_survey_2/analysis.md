## 1. Executive Summary

This investigation analyzed the MSIX packaging project (`FluentFlyoutMSIX.wapproj`), the package manifest (`Package.appxmanifest`), the core WPF project (`FluentFlyout.csproj`), the solution configuration (`FluentFlyout.sln`), the CI workflow (`.github/workflows/build-msix.yml`), and the companion installer script and zip layout (`Add-AppDevPackage.ps1`, `SystemFiles`, `FluentFlyout_Installer.bat`).

### Core Findings at a Glance:
1. **WPF Build Success**: `dotnet build FluentFlyoutWPF/FluentFlyout.csproj -c "GitHub Release" -p:Platform=x64` succeeds cleanly with **0 errors and 0 warnings** in 1.32s under the installed .NET 10 SDK (`10.0.401`).
2. **Build Configuration & Premium Unlock**: The `"GitHub Release"` configuration defines the preprocessor symbol `GITHUB_RELEASE` in `FluentFlyout.csproj:20-22`. In `FluentFlyoutWPF/Classes/LicenseManager.cs:87-92`, this symbol directly sets `_isStoreVersion = false` and `_isPremiumUnlocked = true`, ensuring premium features are unlocked out-of-the-box in GitHub releases.
3. **Wapproj MSBuild Engine Requirement**: `FluentFlyoutMSIX.wapproj` is an MSBuild DesktopBridge project (`C7167F0D-BC9F-4E6E-AFE1-012C56B48DB5`) targeting .NET Framework 4.5.1 for its build tooling. It cannot be built using `dotnet build` or `dotnet msbuild` because the DesktopBridge tasks (`GetFrameworkSdkPackages`, `Microsoft.Build.DesktopBridge.Tasks.dll`) are compiled for .NET Framework.
4. **Toolchain Version Conflict between MSBuild 17 and .NET 10**: The solution file was authored with Visual Studio 18 (`VisualStudioVersion = 18.3.11222.16`). When full-framework `MSBuild.exe` from Visual Studio Community 2022 (v17.14) evaluates `FluentFlyoutMSIX.wapproj`, it fails because .NET SDK 10 (`10.0.401`) strictly enforces `minimumMSBuildVersion = 18.0.0`.
5. **Critical Flaw in CI Packaging Mode**: `.github/workflows/build-msix.yml` line 55 specifies `/p:UapAppxPackageBuildMode=StoreUpload` and line 57 specifies `/p:AppxPackageSigningEnabled=false`. `StoreUpload` creates Microsoft Store packages (`.appxupload`) and **never** generates the `*_Test` sideload directory. Lines 63-65 then try to move `*_Test` to `SystemFiles`, causing `Move-Item` to fail because `$testFolder` is null. For sideloading and `Add-AppDevPackage.ps1` generation, the mode must be `SideloadOnly` (or `SideLoadOnly`).
6. **Certificate Handling**: In `build-msix.yml`, a certificate secret is decoded to `$env:RUNNER_TEMP\cert.pfx`, but MSBuild is passed `/p:AppxPackageSigningEnabled=false` and `/p:PackageCertificateKeyFile` is never specified. Without signing, Windows refuses to install the package, and `Add-AppDevPackage.ps1` cannot function.
7. **`Add-AppDevPackage.ps1` Origin & Layout**: The script is not committed in git; it is automatically generated by Visual Studio / MSBuild DesktopBridge targets from `C:\Program Files\Microsoft Visual Studio\2022\Community\Msbuild\Microsoft\VisualStudio\v17.0\AppxPackage\Add-AppDevPackage.ps1` into the `*_Test` folder alongside `Add-AppDevPackage.resources\`, `Dependencies\`, the `.cer` certificate, and the `.msixbundle`.
8. **In-App Updater Script Execution Gaps**: `UpdateInstallerService.cs` extracts the zip and generates `apply.ps1` to invoke `SystemFiles\Add-AppDevPackage.ps1`. However, `apply.ps1` is executed without `-ExecutionPolicy Bypass`, without logging stdout/stderr, without `-SkipLoggingTelemetry`, and without relaunching the app upon completion.

## 4. MSIX Signing and Certificate Configuration

### 4.1 Strict Matching Rules for MSIX Sideloading
Under Windows App Model rules:
1. **Publisher Subject Match**: The certificate's Subject string MUST match the manifest `<Identity Publisher="..." />` byte-for-byte.
   - Required Subject: `CN=49793F74-1457-4B66-A672-4ED3A640FC76`
   - If there is any character mismatch, `SignTool` fails during packaging.
2. **Trust Store Placement**: For unmanaged sideload installations, the certificate must exist in:
   - `Cert:\LocalMachine\TrustedPeople` (or `Cert:\CurrentUser\TrustedPeople` on Windows 11).
3. **Enhanced Key Usage (EKU)**: Must contain Code Signing (`1.3.6.1.5.5.7.3.3`, OID `szOID_PKIX_KP_CODE_SIGNING`).

### 5.3 Manual vs Automated Installer Behavior
1. **Manual User Installation (`FluentFlyout_Installer.bat`)**:
   ```bat
   cd /d "%~dp0SystemFiles"
   PowerShell -NoProfile -ExecutionPolicy Bypass -Command "& './Add-AppDevPackage.ps1' -SkipLoggingTelemetry"
   PowerShell -Command "& { $pkg = Get-AppxPackage '%AppNamePattern%' | Select-Object -First 1; if ($pkg) { $exe = Join-Path $pkg.InstallLocation 'FluentFlyout\FluentFlyout.exe'; Start-Process $exe } else { Write-Host 'Could not find installed App.' } }"
   ```
   - Changes working directory to `SystemFiles`.
   - Runs `Add-AppDevPackage.ps1` with `-ExecutionPolicy Bypass` and `-SkipLoggingTelemetry`.
   - If not elevated and certificate needs installation, `Add-AppDevPackage.ps1` requests UAC elevation.
   - Upon completion, finds the package install location and launches `FluentFlyout\FluentFlyout.exe`.

2. **In-App Auto-Updater (`UpdateInstallerService.cs`)**:
   In `UpdateInstallerService.ApplyRun`:
   ```csharp
   var extractDir = Path.Join(runDir, "files");
   var zipPath = Path.Join(runDir, "update.zip");
   var installerScript = Path.Join(extractDir, "SystemFiles\\Add-AppDevPackage.ps1");
   var applyScript = Path.Join(runDir, "apply.ps1");

   var scriptBody =
       "Expand-Archive -LiteralPath " + Quote(zipPath) + " -DestinationPath " + Quote(extractDir) + "\r\n" +
       "& " + Quote(installerScript) + "\r\n";

   File.WriteAllText(applyScript, scriptBody);
   _ = Process.Start("powershell.exe", "-NoProfile -File \"" + applyScript + "\"");
   Application.Current.Shutdown();
   ```

### 5.4 Defects Identified in `UpdateInstallerService.cs`:
1. **Missing `-ExecutionPolicy Bypass`**: `Process.Start("powershell.exe", "-NoProfile -File ...")` fails on systems where execution policy is Restricted or RemoteSigned.
2. **Missing Output & Error Logging**: Neither `Expand-Archive` nor `Add-AppDevPackage.ps1` outputs are captured to a log file. If extraction or installation fails, no diagnostic information is available.
3. **No App Relaunch**: `Add-AppDevPackage.ps1` only installs the package; it does not relaunch the application. Once `Application.Current.Shutdown()` occurs, the user must manually locate and relaunch the app.
4. **Synchronous Blocking in `RunAndWait`**: `RunAndWait` is called directly on the calling thread with `process.WaitForExit()`, blocking the WPF UI thread when invoked from `ShowUpdateChoiceAndApplyAsync`.
5. **Console Window Popping**: `RunAndWait` starts `curl.exe` and `powershell.exe` without `ProcessStartInfo` setting `CreateNoWindow = true` and `UseShellExecute = false`.
6. **Sha256 Subprocess Overhead**: Spawning `powershell.exe` to run `Get-FileHash` is slow and fragile; C#'s `System.Security.Cryptography.SHA256` can compute the hash asynchronously in milliseconds.

## 8. Actionable Recommendations for Implementation Phase

1. **Fix `build-msix.yml` MSBuild Parameters**:
   - Change `UapAppxPackageBuildMode` to `SideloadOnly`.
   - Set `AppxPackageSigningEnabled=true`.
   - Provide fallback certificate generation if `secrets.MSIX_CERT_BASE64` is not configured.
   - Pass `/p:PackageCertificateKeyFile` and `/p:PackageCertificatePassword`.
2. **Refactor `UpdateInstallerService.cs`**:
   - Make download and SHA-256 calculation fully asynchronous without blocking the UI thread.
   - Use `System.Security.Cryptography.SHA256` in C# rather than spawning `powershell.exe`.
   - In `apply.ps1`:
     - Invoke powershell with `-ExecutionPolicy Bypass`.
     - Pass `-SkipLoggingTelemetry` to `Add-AppDevPackage.ps1`.
     - Redirect all output and errors to a persistent log file (`update_install.log` in `runDir`).
     - Add app relaunch logic after package installation using `Get-AppxPackage` and `Start-Process`.
3. **Verify CI Toolchain Compatibility**:
   - Ensure GitHub Actions runner sets up .NET 10 SDK and appropriate MSBuild/Visual Studio components so that both `FluentFlyoutWPF` and `FluentFlyoutMSIX` compile cleanly.
